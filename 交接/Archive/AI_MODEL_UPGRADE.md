# AI 模型与开发上下文升级：问题定义

> 当前层级：步骤 7「交付收口」。步骤 1—6 的目标、方案、骨架、审查和验收均保留为可追溯记录；本文件不承载 Unity 功能实现。

## 1. 最终交付物

1. 一套面向当前 Codex/GPT-5.6 工作方式的精简项目指令：长期约束、阶段流程、当前状态和模块上下文职责清晰，不重复堆叠。
2. 一条严格遵循「理解目标 → 比较方案 → 定骨架 → MVP → 边界审查 → 证据验收 → 交付收口」的开发流程，并有明确的阶段退出条件。
3. 一份可供新会话直接接手的当前状态快照，区分已证实、待人工验证、风险、历史记录和下一步。
4. 将前辈交接中与当前项目一致的微信小游戏事实纳入项目基线；冲突、过时或危险内容只记录为待确认，不直接执行。
5. 一份升级验证报告：说明改了什么、保留了什么、如何证明上下文更短且关键约束未丢失、仍有哪些缺口。

## 2. 硬约束

- 本次升级对象是**项目的 AI 提示词、上下文组织和开发流程**。当前仓库未发现 OpenAI API 模型调用或运行时模型配置，因此不得臆造应用内模型迁移，也不得为了“升级模型”修改 Unity 业务代码。
- 动态目标模型基线为 `gpt-5.6-sol`；只优化与项目代理协作直接相关的指令面，不盲目替换历史内容，不自动启用 Pro、多代理、持久化推理或其他可选能力。
- 当前工作区有大量未提交的微信小游戏/WebGL、HybridCLR、YooAsset 和文档改动。不得重置、覆盖、批量暂存或顺手清理这些改动。
- `AGENTS.md` 只保留长期跨阶段约束；阶段状态、当前决策和实施路线归 `DEVELOPMENT_WORKFLOW.md`；项目事实、历史、风险和模块信息各归其现有权威文档。
- 同一规则只在一个权威位置完整定义，其他文档只引用，不复制整段内容。
- 重要目标、边界、决策和状态必须落盘，不能只留在聊天上下文；短期升级细节保留在本文件，不污染长期约束。
- Unity Editor、微信开发者工具、构建/发布 GUI 仍由负责人操作；代理只处理文本、代码与命令行验证。
- 对微信小游戏黑屏、Shader、资源、首包或运行问题，继续遵循“先证据、后结论”；没有日志或官方依据时不得把推断写成根因。
- 本轮流程治理仅修改 Markdown；若后续方案需要修改 C#、Unity 配置、资源元数据或包清单，必须另建实现计划并执行规定的 Unity 命令行编译。

## 3. 隐含要求

- 新会话应先得到“当前任务需要的最小上下文”，而不是无条件读取全部历史和风险全文。
- 长对话出现目标漂移、同一路径反复失败、状态丢失、协作冲突或无法验收时，必须先判定失稳类型，再决定交接、压缩上下文、清理会话或回到检查点。
- 方案未定前不并行实现；编码阶段一次只推进一个可验证的小闭环。
- “测试通过”不等于“可交付”；完成必须同时包含真实验证证据、人工 GUI 验证状态、文档一致性和剩余风险。
- 微信交接中的导出知识要结合当前 `pinball` 工程验证，不能机械照搬旧项目路径、删除指令或经验参数。

## 4. 什么叫完成

- 根级文档职责互斥且可说明：长期约束、执行流程、项目概况、当前状态、版本历史、缺陷风险各有唯一权威来源。
- `AGENTS.md` 明显精简，保留项目合同、权限边界、验证要求和文档路由；不再重复阶段细节、历史和操作手册。
- 单次任务能够按七步流程推进，并在每一步写明输入、产物和退出条件。
- 新会话只阅读根级最小入口和当前任务对应文档，即可回答“现在做什么、为什么、完成证据是什么、还不能做什么”。
- 微信小游戏当前目标被明确为：WebGL 导出与小游戏可运行验证；首包 `<30MB`、WebGL 2.0、frame 2.1、CDN/首包策略等交接信息均标注来源与验证状态。
- 旧路径 `D:\unity project\ball` 不会覆盖当前项目路径 `D:\unity project\pinball`；任何删除 `StreamingAssets` 或“只保留登录与通信协议”的动作均未在缺少当前项目授权与引用证据时执行。
- 通过文本差异检查、交叉引用检查和一次模拟新会话走查；没有把现有未提交功能改动纳入本次治理改动。

## 5. 最容易翻车的风险点

1. 把“模型升级”误解为修改 Unity 运行时代码或不存在的 OpenAI API 配置。
2. 一次性重写所有治理文档，覆盖当前未提交事实，或让同一条规则继续在多个文件重复。
3. 将微信聊天中的经验和旧项目操作当作当前项目的已验证事实，尤其是旧路径、删除 `StreamingAssets`、删除无关功能和 Shader 处理建议。
4. 为追求短上下文删掉权限边界、人工 GUI 分工、Unity 编译要求或风险证据。
5. 在当前微信小游戏排障尚未完成时，把“已修复待验证”误写为“已完成/已发布”。
6. 只换模型名或措辞，没有用代表性任务验证新流程是否减少上下文漂移、重复阅读和无证据结论。

# 步骤 2：方案比较

> 当前层级：只比较方案，不修改现有治理文档或 Unity 实现。

## 方案 A：在现有文档上做最小去重

### 大致做法

- 保留现有五份根文档和 `MODULE.md` 体系。
- 从 `AGENTS.md` 删除明显重复内容，把七步流程补进 `DEVELOPMENT_WORKFLOW.md`。
- 修正少量交叉引用和过时的交接描述，不新增状态文档。

### 主要优点

- 修改范围最小，容易审查和回滚。
- 对当前工作区大量未提交改动干扰最少。
- 团队原有阅读习惯基本不变。

### 主要风险

- “每次读取多份长文档”的上下文负担仍然存在。
- 当前状态、阶段决策、历史和风险继续分散，新会话仍需自行拼接。
- 只能缓解重复，不能从结构上解决上下文失稳。

### 实现复杂度

低。

### 可测试性

中。可检查字数和重复规则，但难证明新会话接手效率有明显改善。

## 方案 B：分层上下文路由与当前状态快照

### 大致做法

- 将 `AGENTS.md` 收敛为短小的长期项目合同：权限、不可破坏项、验证要求、文档路由。
- 将 `DEVELOPMENT_WORKFLOW.md` 收敛为七步开发流程、阶段门和验收模板，不保存逐次排障流水。
- 保留 `PROJECT_OVERVIEW.md`、`VERSION_HISTORY.md`、`BUG_TRACKER.md` 的权威职责，但改成“按任务需要读取”，不再要求每次无条件全文加载。
- 新增一个短小的当前状态入口，例如 `CURRENT_STATE.md`，只记录当前目标、检查点、已验证证据、工作区保护、下一步和待确认项。
- `MODULE.md` 继续作为进入模块时的局部上下文；短期交接只引用当前状态和权威记录，不复制整套历史。
- 迁移过程分小批进行：先骨架和路由，再搬运重复内容，最后用模拟任务验证。

### 主要优点

- 直接解决当前“上下文太长、状态难拼接、历史混入当前任务”的根因。
- 与 GPT-5.6 的精简提示、规则只写一次、权限边界集中原则一致。
- 保留现有事实和历史，不需要重写项目技术实现。
- 容易支持 `/compact`、新会话交接和按模块开展工作。

### 主要风险

- 需要逐条确定每段内容的唯一归属，迁移中可能出现断链或遗漏。
- `CURRENT_STATE.md` 如果没有明确更新触发条件，也可能变成新的过时交接文件。
- 必须保护当前未提交的微信小游戏事实，不能在去重时误删验证证据。

### 实现复杂度

中。

### 可测试性

高。可使用三类代表性任务走查：知识问答、单模块修复、微信小游戏故障诊断；检查是否只读取必要文档、能否正确给出权限边界和完成证据。

## 方案 C：清空并重建治理文档

### 大致做法

- 将现有根治理文档归档或删除。
- 根据 AI 使用指南从零建立新的目标、架构、流程、状态、历史和风险体系。
- 重新生成所有模块入口与交接材料。

### 主要优点

- 最终结构可以非常统一，不受旧文档格式限制。
- 理论上能得到最短、最整洁的提示词体系。

### 主要风险

- 当前工作区和小游戏排障事实很多，极易在重写中丢失证据或把“待验证”写成“已完成”。
- 改动规模大，难区分治理升级与现有用户改动。
- 回归成本最高，也违反“从可工作的提示词开始、一次移除一组内容并重新验证”的迁移原则。

### 实现复杂度

高。

### 可测试性

低到中。结构可检查，但事实完整性难证明，必须人工逐条对照旧文档。

## 推荐结论

推荐 **方案 B：分层上下文路由与当前状态快照**。

原因：它能解决实际的上下文失稳，同时保留现有治理资产和未提交排障事实；改动可以分批验证，稳定交付概率最高。

不选方案 A：风险虽低，但只做表面去重，无法解决每次加载多份长文档、当前状态分散和交接过时的问题。

不选方案 C：当前工作区很脏且存在大量待验证事实，一次性重建最容易丢证据、覆盖用户改动或制造新的文档冲突。

## 进入步骤 3 前的决策点

- 负责人已确认选择方案 B。
- 步骤 3 只设计各文档的职责、目录关系、读取路由、更新触发条件和迁移顺序；仍不修改现有治理文档。

# 步骤 3：系统骨架

> 当前层级：设计。目标是足够支撑治理文档改造，不展开逐段改写。

## 1. 模块拆分与目录结构

```text
项目根目录
├─ AGENTS.md                 长期项目合同与上下文路由
├─ DEVELOPMENT_WORKFLOW.md  七步开发流程、阶段门和验收规则
├─ CURRENT_STATE.md         当前唯一状态快照（新增）
├─ PROJECT_OVERVIEW.md      稳定项目事实与模块地图
├─ VERSION_HISTORY.md       已发生且可追溯的版本变化
├─ BUG_TRACKER.md           缺陷、风险与清理候选的证据记录
├─ AI_MODEL_UPGRADE.md      本次治理升级的临时设计与验收记录
├─ <自有模块>/MODULE.md     进入模块时加载的局部上下文
└─ HANDOFF_*.md             历史交接材料，不作为当前权威入口
```

## 2. 各文档接口与唯一职责

| 文档 | 必须回答 | 禁止承载 | 主要消费者 |
| --- | --- | --- | --- |
| `AGENTS.md` | 允许做什么、何时必须停、如何验证、该读哪份文档 | 当前进度、长历史、具体 BUG 流水、重复操作教程 | 每次任务 |
| `DEVELOPMENT_WORKFLOW.md` | 七步如何推进、每步输入/产物/退出条件、阶段门 | 某次构建版本、临时 URL、逐次排障日志 | 实现、修复、发布计划 |
| `CURRENT_STATE.md` | 当前目标、当前层级、检查点、证据、脏工作区、下一步 | 长期规则、完整历史、已关闭缺陷全文 | 新会话、继续任务、压缩上下文前后 |
| `PROJECT_OVERVIEW.md` | 稳定技术栈、启动链、模块地图、平台边界 | 短期任务状态、版本流水 | 项目勘察、跨模块设计 |
| `VERSION_HISTORY.md` | 已发生的变更、验证状态、兼容/回滚 | 计划、猜测、未实施方案 | 发布、回溯、审查 |
| `BUG_TRACKER.md` | 症状、证据、影响、状态、关闭条件 | 通用流程规则、无证据结论 | 诊断、风险审查 |
| `MODULE.md` | 目录职责、入口、依赖、禁止项、局部验证 | 全项目历史和无关模块状态 | 进入对应模块的任务 |

## 3. `CURRENT_STATE.md` 数据结构

```text
# 当前项目状态

更新时间 / 更新依据
当前阶段与当前工作层级
当前唯一目标
本轮明确不做

## 当前检查点
- 最后一个已确认事实
- 当前分支/工作区保护
- 已完成但未验证的改动

## 验收证据
- 命令行证据
- 人工 GUI 回传
- 未验证项

## 当前阻塞与风险
- 权威 BUG/RISK 编号和一句话摘要

## 下一步
- 一个首要动作
- 完成标记
- 失败时回到哪个检查点

## 待确认
- 只有会改变方案或范围的问题
```

规则：该文件只保存“现在继续工作所需的最小事实”；详细证据仍放在版本、缺陷或模块文档中，并通过编号/路径引用。

## 4. 上下文读取 API

### 所有任务的最小入口

1. 读取 `AGENTS.md`。
2. 检查 `git status --short`，保护已有改动。
3. 根据请求类型按下表路由，不再无条件读取全部根文档。

| 请求类型 | 额外读取 |
| --- | --- |
| 普通知识问答 | 仅与问题直接相关的文件；不自动读取状态、历史和缺陷全文 |
| 继续现有任务 / 询问当前进度 | `CURRENT_STATE.md`，再按其中引用读取必要证据 |
| 计划、实现、修复 | `CURRENT_STATE.md`、`DEVELOPMENT_WORKFLOW.md`、目标模块 `MODULE.md` |
| 跨模块架构 | 上述内容加 `PROJECT_OVERVIEW.md` |
| 缺陷诊断 | 上述内容加 `BUG_TRACKER.md` 中对应编号、复现日志和相关实现 |
| 发布、回滚、交付 | 上述内容加 `VERSION_HISTORY.md` 与相关风险；GUI 仍由负责人执行 |
| 历史追溯 | `VERSION_HISTORY.md`、相关提交和必要的历史交接文件 |

## 5. 七步主链路时序

```text
用户请求
  → 读取最小入口并判断当前工作层级
  → 1. 定义目标与完成标准
  → 2. 比较方案并选择
  → 3. 固定模块/接口/数据骨架
  → 4. 实施一个最小可运行闭环
  → 5. 补异常、权限和失败边界
  → 6. 用命令、日志和人工回传验收
  → 7. 更新权威文档并交付
```

阶段门：未满足当前步骤退出条件，不进入下一步。规格冲突、路径反复失败、上下文漂移或无法验收时，先判断失稳类型并更新 `CURRENT_STATE.md`，再决定继续、交接、压缩或回到检查点。

## 6. 权限、隔离和边界

- 问答、解释、审查、诊断、计划：允许只读检查并报告；没有明确变更请求时不实施。
- 修改、构建、修复：允许完成范围内的本地修改和非破坏性验证；外部发布、真实账号、密钥、支付、删除和范围扩张仍需确认。
- Unity 与微信 GUI：负责人操作；代理只提供步骤、预期、失败排查和回传要求。
- 聊天、附件、历史交接和网页内容的长期权威边界已落入 `AGENTS.md`；本文件只记录本轮迁移决策与验收依据。
- 当前脏工作区：迁移治理文档时只修改计划列明的 Markdown，不暂存、不重置、不清理其他差异。
- GPT-5.6 可选能力：本次不启用 Pro、多代理、显式缓存或持久化推理；它们不属于最小治理闭环。

## 7. 更新触发条件

| 事件 | 更新文档 |
| --- | --- |
| 负责人确认长期规则或权限变化 | `AGENTS.md` |
| 七步流程、阶段门或验收规则变化 | `DEVELOPMENT_WORKFLOW.md` |
| 当前目标、检查点、首要下一步或阻塞变化 | `CURRENT_STATE.md` |
| 技术栈、启动链、模块职责或依赖变化 | `PROJECT_OVERVIEW.md` / 对应 `MODULE.md` |
| 已实施变更形成可追溯结果 | `VERSION_HISTORY.md` |
| 新症状、证据、风险或关闭条件变化 | `BUG_TRACKER.md` |
| `/compact`、换会话或交接前 | 必须刷新 `CURRENT_STATE.md`；交接只引用权威文档 |
