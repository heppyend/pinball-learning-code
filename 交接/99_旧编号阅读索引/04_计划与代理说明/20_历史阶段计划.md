## 3. 目标 UI 架构

`ClientCanvas` 是客户端业务 UI 的唯一宿主。所有客户端可见对象必须归入以下三层之一；运行时不得为业务需求在层外临时生成第二套页面根。

```text
ClientCanvas
├─ PagesLayer       互斥的可导航页面
│  └─ 一个时刻仅当前页（及明确的转场宿主）可见
├─ PopupLayer       可叠加、可关闭、带遮罩/阻断语义的业务弹窗
│  └─ 由统一弹窗栈管理，关闭后恢复调用方状态
└─ SystemLayer      跨页面全局界面
   ├─ Loading / 阻断遮罩
   ├─ Toast / Tips
   ├─ 红点或全局状态提示
   └─ 网络、重连、维护等系统级提示（若需求确认）
```

### 3.1 分层责任边界

| 层 | 应放内容 | 不应放内容 | 生命周期 |
| --- | --- | --- | --- |
| `PagesLayer` | 大厅、英雄、背包、养成、商城、邮箱、排行榜、活动、任务、扭蛋、个人中心等完整页面 | 确认框、规则说明、Toast、全局加载、跨页遮罩 | 统一页面导航器维护路由、返回栈、Enter/Pause/Resume/Exit。 |
| `PopupLayer` | 详情、规则、领取确认、筛选、购买确认、奖励展示等业务弹窗 | 页面根、全局 Loading、独立业务导航器 | 统一弹窗服务维护栈、遮罩、输入阻断、返回/关闭和回调。 |
| `SystemLayer` | Loading、Toast、通用提示、全局遮罩与系统错误展示 | 具体业务页面或业务详情弹窗 | 独立于页面切换；必须可恢复、可取消监听、不可遗留输入阻断。 |

### 3.2 必须消除的结构问题

1. 不再把导航页面、弹窗和全局界面混合放在 `PagesLayer`。
2. 不允许同一功能存在两个并行导航控制器、旧 `SetActive` 回调与新导航器同时控制可见性。
3. 不允许页面直接持有运营数值、发奖/扣币规则或支付流程；页面只调用共享服务接口并刷新视图。
4. 不允许 `Update` 轮询业务状态或隐式全局查找；使用明确的绑定、刷新入口和退出解绑。
5. 不允许改动 GUI 节点、素材或版式来“顺便”修架构，除非任务明确授权写入场景；默认只调整脚本与现有引用。

## 4. 阶段 A：UI 与本地逻辑实施路线

### A0：只读基线盘点与冻结点

在写任何功能前完成以下产物：

- 保存 `git status --short`、当前分支/提交、Unity 版本、已修改和未跟踪文件清单；不以“脏数据”为由删除内容。
- 建立页面清单：场景节点路径、控制脚本、入口、返回目标、数据服务、弹窗、当前状态、证据、负责人确认状态。
- 建立 UI 根节点清单：所有 Canvas、`PagesLayer`/`PopupLayer`/`SystemLayer` 子节点、排序、独立 Canvas、运行时实例来源和重复显示风险。
- 列出实际导航/弹窗/提示/加载入口，标记旧实现、唯一保留实现和迁移顺序。
- 将已知缺陷、待清理候选、未确认需求分别写入权威问题记录；不得混写为已完成事项。

**验收：** 基线快照可复查；任何后续改动均能区分为既有内容或本计划新增内容。

### A1：共享 UI 内核收敛

只保留一套共享的：

- 页面 ID、页面注册、路由、返回栈与生命周期；
- 弹窗 ID、弹窗栈、遮罩、输入阻断、关闭与回调；
- Loading、Toast/Tips、红点、货币校验和通用反馈；
- 领域模型、可替换数据服务和本地模拟数据；
- 资源加载适配边界（继续遵守 YooAsset 生命周期，不提前替换加载基础设施）。

迁移必须以功能小批次进行：先用运行日志/场景引用证明某一旧控制入口被唯一替代，再移除其调用；不能用大范围 `SetActive(false)` 掩盖重复页面问题。

**验收：** 任意页面切换、弹窗开关、全局 Loading 均有唯一所有者；返回和关闭顺序可测试；不会留下遮罩、监听或输入阻断。

### A2：页面与状态闭环

按交互稿及盘点后形成的页面矩阵逐项完成。推荐按依赖和复用关系推进，而不是按场景文件杂乱程度推进：

1. 大厅、全局入口、个人中心；
2. 英雄、图鉴、背包、英雄详情；
3. 养成、装备、材料与资源不足反馈；
4. 商城、邮箱、排行榜；
5. 活动、任务、扭蛋及奖励入库本地模拟；
6. 通用弹窗、筛选/排序、规则页、奖励展示、红点和全局提示收口。

每个页面至少验证：加载、空数据、拥有/未拥有、锁定/解锁、资源不足、限购（如适用）、活动未开启/已结束（如适用）、成功/失败、返回和关闭。未定义的数值、活动周期、奖池、支付和服务端确认必须保留配置/接口位并登记待确认。

**验收：** 页面矩阵每行都有可复现入口、状态证据和验证记录；不存在用同一临时页面冒充多个最终页面的情况。

### A3：代码可维护性与测试

- 将纯逻辑规则（筛选、资源扣减校验、限购、奖励领取、状态迁移）拆至可测试服务或领域层。
- 为高风险逻辑添加自动化测试；页面交互以独立客户端场景和人工回归清单验证。
- 为页面、服务、UI 内核目录维护 `MODULE.md`：职责、入口、依赖、禁止事项、验证方法和待确认项。
- 仅对非显然意图、状态约束、平台分支和历史兼容原因添加简洁代码注释；不以重复代码表面含义的注释充数。

## 5. 阶段 B：微信小游戏迁移与真机测试

### B0：迁移前门禁

在 UI 闭环可稳定运行前，不把 WebGL 构建失败当成 UI 问题修补。先确认并留档：

- Unity 与微信小游戏转换工具/SDK 的实际版本、安装位置、授权方式和现有导出链路；
- WebGL 平台差异：线程/网络、文件系统、浏览器 API、压缩、内存、纹理/Shader、音频、字体、输入、URL/资源加载；
- YooAsset、HybridCLR、XLua 与微信小游戏的当前兼容矩阵和已有项目适配代码；
- 分包、资源地址、首包预算、远端资源策略和回收生命周期；
- 真实设备、微信版本、网络环境、测试账号（如确有必要）和日志回传方式。

任何平台问题必须先引用当前微信官方文档、SDK 实现或最小可回收诊断日志；证据不足时只记录采集项，不将推断写成根因。

### B1：可复现构建链路

建立一个不包含发布/上传权限的本地构建说明和检查清单：

```text
Unity ClientShell 验证
  → WebGL 构建
  → 微信小游戏转换/导入
  → 开发者工具本地预览
  → 真机预览或体验版测试（由获授权人员执行）
  → 日志、性能与问题证据归档
```

不把密钥、AppID、服务端地址、token、订单或个人资料写入仓库、命令输出或演示数据。涉及上传、真实账号、发布、支付和不可逆后台操作时，由负责人单独授权并手动执行。

### B2：真机回归矩阵

最低覆盖：

| 类别 | 真机验收点 |
| --- | --- |
| 启动 | 首次启动、资源初始化、Loading 完成/失败/重试、后台切回。 |
| UI | 分辨率与安全区、横竖屏策略、字体、触摸、滚动、返回、遮罩和输入阻断。 |
| 导航 | 页面互斥、返回栈、弹窗栈、Toast/Loading 不残留。 |
| 数据 | 本地模拟数据初始化、空态、奖励/货币刷新、存档边界（若需求确认）。 |
| 资源 | 首包、分包/下载、缓存、资源失败提示、内存峰值和回收。 |
| 平台兼容 | WebGL/小游戏不支持 API、网络限制、音频/渲染/Shader、异常日志。 |
| 稳定性 | 连续页面跳转、重复开关弹窗、弱网/断网（如适用）、冷启动与热重进。 |

每个结果需记录设备型号、系统、微信版本、构建标识、复现步骤、截图/日志路径、结论和下一动作。未测试不能标记通过。
